**Vérifié de bout en bout le 29/10/2026** : bouton « Se connecter avec Nexora AI » dans WorkStudio → connexion du site → retour à WorkStudio (espace de travail créé) → clé `nxk_` par personne créée par `GET /api/oauth/workstudio-access` → message à l'assistant → réponse via la passerelle du site (LiteLLM de dév.) → débit du portefeuille. - Pont `litellm-pc1-pont.service` : LiteLLM de pc1 (4400) → `172.17.0.1:18090` pour le LiteLLM de dév. du site (`PC1_UPSTREAM_URL=http://host.docker.internal:18090`) ; sans lui, tout appel de modèle de dév. donne 502.
- Modèle d'essai `nexora/essai-dev` (non listé, prix fictifs, fournisseur `dev-litellm`) dans `app_demo` : à RETIRER avant la vraie mise en service (et le crédit de test, l'utilisateur d'essai).

Pièges appris : (1) avec `cacheComponents` une route GET qui lit l'environnement sans toucher aux en-têtes est PRÉPARÉE AU BUILD et fige un 404 → `await connection()` en première ligne (`export const dynamic` est interdit) ; vérifier « ƒ » dans la sortie de `next build`. (2) Témoins de session : le site utilise le préfixe `nexora-site` pour ne pas écraser ceux de WorkStudio sur un même hôte. (3) WorkStudio demande la clé du site au premier appel de modèle (jeton de 10 min), pas à la connexion. (4) Docker Hub a des pannes DNS sur pc1 : réessayer le `docker pull`. (5) `NEXORA_UPSTREAM_KEY` de pc1 `.env` s'affiche si on fait un grep sans masque : ne jamais grep ce fichier sans `cut -d= -f1`.
